# Пробное практическое интервью

Задача на 45–60 минут по обработке данных для backend. Уточни контракт, напиши реализацию и только затем сравни её с ответом.

Рабочий вариант есть в `examples/core.ts`, тесты — в `examples/core.test.ts`. Блоки кода ниже используют общий контекст.

## Условие

Напиши `importUpdates(raw, repository, concurrency)`. На вход приходит `readonly unknown[]`.

Валидное обновление содержит:

- `sourceId` — непустую строку, не состоящую только из пробелов: источник или система, приславшая обновление.
- `eventId` — непустую строку, не состоящую только из пробелов: событие внутри этого источника.
- `listingId` — непустую строку, не состоящую только из пробелов: сущность внутри этого источника.
- `version` — неотрицательное безопасное целое число, задающее порядок состояний сущности.
- `price` — конечное неотрицательное число. Числовая строка недопустима; ноль допустим.

Ключ состояния — **`(sourceId, listingId)`**. Сохраняй максимальную `version` для каждого ключа. Одинаковые версии неизменяемы и пропускаются. Дополнительных внешних побочных эффектов в этой задаче нет.

Импорт должен:

1. Вернуть ровно один результат на каждый входной элемент, в порядке входа.
2. Для некорректного входа вернуть `invalid` с индексом и объяснением.
3. Для завершённой записи вернуть `applied` либо `stale` с индексом и `eventId`.
4. Для ошибки хранилища вернуть `failed` и продолжить обработку остальных записей.
5. Держать не больше `concurrency` активных вызовов хранилища и дождаться их завершения.
6. Не менять входные объекты.

`concurrency` должен быть положительным целым числом. Некорректное значение отклоняет весь вызов, даже при пустом входе. Ошибки отдельных записей попадают в отчёт.

**Не удаляй повторы `eventId` перед обработкой.** Здесь нужен результат для каждого входа. Атомарное условие версии обеспечивает идемпотентность состояния; дедупликация доставки — отдельный контракт.

## Стартовые типы

`Repository.upsertIfNewer` должен быть **атомарным**: сравнение версии и запись происходят одной операцией хранилища. Отдельные чтение и запись в импортёре эту гарантию не заменяют. Реализовывать настоящую БД здесь не нужно.

Раздели обязанности:

- `parseUpdate` проверяет внешнее значение и возвращает новый `ListingUpdate`.
- `mapLimit` ограничивает активную работу и сохраняет позиции результатов.
- `importUpdates` превращает ожидаемые ошибки записей в значения отчёта.

```ts
type ListingUpdate = {
  sourceId: string;
  eventId: string;
  listingId: string;
  version: number;
  price: number;
};

interface Repository {
  upsertIfNewer(update: ListingUpdate): Promise<"applied" | "stale">;
}

type ImportResult =
  | { status: "applied" | "stale"; index: number; eventId: string }
  | { status: "invalid"; index: number; message: string }
  | { status: "failed"; index: number; eventId: string; message: string };
```

## Практика

Напиши parser, ограничитель и импорт до открытия ответа. Включи такие случаи:

- Сущность A/v5, затем A/v3.
- Невалидная числовая строка и допустимый ноль.
- Сущность B/v1, при записи которой хранилище падает.
- Повтор обновления A/v5.
- Некорректная конкурентность, в том числе при пустом входе.

Проверь порядок результатов, конечные версии и завершение активной работы. Различай гарантию конечного состояния и классификацию отдельных записей.

### Спойлер

Если A/v5 применяется раньше A/v3, результаты будут `applied` и `stale`. Если v3 успеет первой, обе записи могут вернуть `applied`; конечное состояние всё равно v5.

**Контракт гарантирует максимальную конечную версию, а не одинаковую классификацию каждой записи при любом расписании.** Невалидный вход даёт `invalid`, сбой B — `failed`, равная версия не меняет состояние.

```ts
async function importUpdates(
  raw: readonly unknown[],
  repository: Repository,
  concurrency: number,
): Promise<ImportResult[]> {
  return mapLimit(raw, concurrency, async (value, index): Promise<ImportResult> => {
    let update: ListingUpdate;
    try {
      update = parseUpdate(value);
    } catch (error) {
      return { status: "invalid", index, message: messageOf(error) };
    }
    try {
      const status = await repository.upsertIfNewer(update);
      return { status, index, eventId: update.eventId };
    } catch (error) {
      return {
        status: "failed", index, eventId: update.eventId,
        message: messageOf(error),
      };
    }
  });
}

function messageOf(error: unknown): string {
  return error instanceof Error ? error.message : String(error);
}
```

Parser строит новый проверенный объект. Локальные блоки `catch` превращают ошибки записей в результаты, поэтому одна ошибка не останавливает импорт. `mapLimit` сохраняет позиции входа и дожидается активной работы.

## Follow-up: повторная доставка с эффектом

Допустим, при `applied` нужно отправить уведомление. Падение после записи в БД, но до отправки делает повтор `stale`, и уведомление может потеряться.

Нужен надёжный учёт эффекта, например outbox в одной транзакции с обновлением. Доставке всё ещё нужна политика идемпотентности или дедупликации. Одного множества в памяти для надёжной координации недостаточно.

## Follow-up: бесконечный поток

Текущий API хранит вход и выход целиком: **`O(n)` памяти**. Для большого потока используй асинхронную итерацию, ограниченную активную работу и постепенную выдачу или запись отчёта.

Определи backpressure и надёжную контрольную точку. При строгом порядке медленный первый элемент задерживает выдачу следующих, уже готовых результатов; ограничивай и этот буфер, а не только активные задачи.

## Follow-up: порядок на один ключ

Общий лимит конкурентности не сериализует обновления одной сущности. Атомарной записи максимальной версии достаточно для этого контракта выбора состояния.

Инкременты, переходы состояний или промежуточные эффекты могут потребовать очереди по разделам, блокировки ключа либо другой атомарной бизнес-операции. Сначала определи нужный порядок, затем выбирай механизм.

## Follow-up: retry

Повторяй только выбранные временные ошибки операций, безопасных для повтора. Ограничь число попыток и общее время.

Таймаут может означать «записали, но ответ потерялся». Повтор versioned upsert вернёт `stale`, оставив корректное состояние. Если бизнесу важно различие `applied` и `stale`, определи, как отражать неопределённый исход первой попытки.

## Как оценивать свою попытку

Проверь пять вещей:

- **Контракт:** явно ли определены область ключей, равные версии и порядок результатов?
- **Валидация:** корректно ли обрабатываются плохой вход и допустимый ноль?
- **Конкурентность:** ограничена ли активная работа и дожидается ли её вызов?
- **Ошибки:** сохраняются ли остальные результаты и гарантия конечного состояния?
- **Объяснение:** можешь ли ты обосновать реализацию содержательными тестами?

Запусти `npm test` и `npm run check`. Хранилище в памяти — тестовая замена; реальной БД нужны отдельные интеграционные проверки атомарной записи и ограничений.
